# Research: Overload Collapse Mode for Host Nodes (012)

Delta on 011's host model ([011 data-model](../011-host-queue-model/data-model.md), [011 research](../011-host-queue-model/research.md)) and 013's per-replica composition ([013 data-model](../013-host-autoscaling/data-model.md)/[013 research](../013-host-autoscaling/research.md)). This branch merged `dev` (which already contains feature 013, fully implemented, constitution at v3.3.0) before planning — 012 was cut from the 011 merge commit, before 013 existed on `dev`; see the branch-topology note at the end of this file.

## D1 — The knee is `manualMaxRPS` (manual) / the ρ=1 capacity point (calculated) — not `manualSaturationRPS`

**Decision**: The point where clamp and collapse diverge ("the knee") is exactly the point where 011's clamp behavior starts doing anything besides pass-through:
- **Manual mode**: `computeManualMetrics` today is `forwardedRPS = min(incomingRPS, manualMaxRPS)`. Below `manualMaxRPS`, forwardedRPS already equals incomingRPS (no shedding) regardless of `manualSaturationRPS` — that field only ever feeds the latency curve's ρ, not shedding. So the knee is `manualMaxRPS`, not `manualSaturationRPS`.
- **Calculated mode**: there is no existing "cap" field at all — `computeCalculatedMetrics` always forwards 100% of incoming, forever (011's intentional "calculated mode never sheds" design). The only existing threshold is ρ=1, i.e. `kneeRPS = maxWorkerThreads / (inboundWeightedComputeMultiplier * cpuProcessingTimeMs / 1000)` — the same denominator already computed for ρ. This is the calculated-mode analog of `manualMaxRPS`.

Below the knee (either mode): `forwardedRPS = incomingRPS` in both `clamp` and `collapse` — identical by construction, satisfying FR-003/SC-002/the "exactly at the knee" edge case with **exact** (not approximate) value equality, since both branches evaluate to the same expression.

**Rationale**: FR-002 requires `clamp` to reproduce 011 exactly, which pins the knee definition to whatever field 011's shedding logic already keys off. Re-deriving the "knee" as `manualSaturationRPS` would have made clamp and collapse disagree between the saturation point and the max-RPS point — a discontinuity the spec's edge cases explicitly forbid ("clamp and collapse must agree at the knee point itself").

**Alternatives considered**: Using `manualSaturationRPS` (ρ=1) as the knee for manual mode — rejected, contradicts FR-002 (clamp's actual shedding point is `manualMaxRPS`, which is ≥ `manualSaturationRPS` and can be strictly greater per the Inspector's own auto-clamp).

## D2 — Retrograde curve: `decay(x) = 1 / (1 + κ(x−1)²)`, anchored at the knee

**Decision**: Past the knee, `forwardedRPS = kneeRPS × decay(overloadRatio)`, where `overloadRatio = incomingRPS / kneeRPS` (≥ 1 past the knee) and `decay(x) = 1 / (1 + κ(x − 1)²)`, a new internal tunable `HOST_COLLAPSE_DECAY_KAPPA` in `config.ts`. Properties, all required by FR-003/edge cases:
- `decay(1) = 1` ⇒ `forwardedRPS = kneeRPS` exactly at the knee — continuous with the pass-through region below it (C0 continuity, no step).
- Strictly monotonically decreasing for `x > 1`, smooth (infinitely differentiable) — no kink introduced by the curve itself.
- `decay(x) → 0` as `x → ∞`, always in `(0, 1]` — `forwardedRPS` stays finite and `> 0` for any finite offered load, `→ 0` only in the limit (satisfies "approaches zero", "underflows gracefully", never negative/NaN/Infinity).
- Pure function of `incomingRPS` and the host's own declared capacity fields — no state, satisfying FR-010 (stateless recovery, symmetric sweep up/down, SC-004).
- `kneeRPS ≤ HOST_ZERO_CAPACITY_EPSILON` (zero-capacity host) short-circuits to `forwardedRPS = 0` unconditionally, avoiding a divide-by-zero in `overloadRatio` (mirrors the existing zero-capacity guard pattern in `hostModel.ts`).

**κ = 2** (`HOST_COLLAPSE_DECAY_KAPPA`), chosen to satisfy SC-001's numeric bar: at 3× the knee, `decay(3) = 1/(1+2·4) = 1/9 ≈ 11%` of peak (< 20% required); at 5×, `decay(5) ≈ 3%`; at 100×, `decay(100) ≈ 0.005%` — always finite, always positive, never needs clamping.

**Rationale/citations** (constitution II, FR-011): the qualitative shape — throughput rising to a peak then bending back down as offered load keeps rising — is the "retrograde" region of Gunther's Universal Scalability Law (USL) and the general phenomenon of **congestion collapse** / **receive livelock**, where a system that keeps accepting work past its effective capacity spends an increasing share of its capacity on overhead (retries, context switches, interrupt handling) instead of useful work, so *goodput* falls even as *offered load* rises. USL's own two-parameter form (`σ` contention, `κ` coherency delay) requires a free "concurrency" variable this product doesn't model per-host and would add two numeric knobs — explicitly forbidden by FR-004. The quadratic-penalty closed form used here is a single-internal-tunable simplification that reproduces USL's qualitative retrograde shape (rise → peak → decay toward zero) without exposing or requiring anything beyond the host's own existing capacity fields. Citations shipped on the descriptor (FR-011):
- Mogul & Ramakrishnan, "Eliminating Receive Livelock in an Interrupt-Driven Kernel" (USENIX 1996 / ACM TOCS 1997) — canonical measurement of goodput collapsing under overload in a real system.
- Gunther, the Universal Scalability Law's retrograde throughput region (Guerrilla Capacity Planning) — the general shape this curve reproduces.

**Alternatives considered**: Literal USL (`X(N) = N/(1+σ(N−1)+κN(N−1))`) — rejected, needs a concurrency variable and two tunables where the spec wants the curve derived from *existing* capacity fields alone; exponential decay `exp(−κ(x−1))` — considered, rejected in favor of the quadratic form only because the quadratic's `decay(x)→0` rate was easier to tune against SC-001's exact numeric thresholds with one clean tunable; both are equally defensible "engine decisions" per the spec's own Assumptions section.

## D3 — Calculated mode gets the same curve, anchored at its own ρ=1 point

**Decision**: `overloadBehavior` is required on **both** `configMode: 'manual'` and `configMode: 'calculated'` variants of the saturating profiles (FR-001 doesn't distinguish by mode). For calculated mode, `kneeRPS = maxWorkerThreads / (inboundWeightedComputeMultiplier × cpuProcessingTimeMs/1000)` (zero if threads/cpuTime/weight aren't all positive) is exactly the incoming rate at which the existing `rho` formula would read 1.0 — so `x = incomingRPS / kneeRPS` is algebraically identical to the existing (unclamped) `rho`. `clamp` + calculated stays byte-identical to 011 (always forwards 100%, per FR-002/SC-003); `collapse` + calculated newly sheds past ρ=1, using the same shared `decay()` helper as manual mode.

**Rationale**: Gives calculated-mode hosts the same teaching value as manual-mode hosts (both saturating profiles can now demonstrate collapse) without inventing a second curve shape or a mode-specific tunable — one shared `collapseForwardedRPS(incomingRPS, kneeRPS)` helper in `hostModel.ts` serves both call sites.

**Alternatives considered**: Leaving calculated mode `collapse`-exempt (always pass-through, matching its 011 "never sheds" identity) — rejected: FR-001/FR-003 apply to the profile regardless of configMode, and users would lose the collapse UI toggle's meaning if switching config mode silently no-opped it.

## D4 — Queue backpressure (`hostAcceptCapacityRPS`) stays completely unchanged

**Decision**: `flowPropagation.ts`'s `hostAcceptCapacityRPS` (used only to size a queue's desired outflow toward a downstream saturating host) is **not touched** — it continues to return `manualMaxRPS × effectiveCount` for manual mode and `Infinity` for calculated mode and `external_api`, identically for `clamp` and `collapse`. This is a deliberate zero-line-diff decision, not an oversight.

**Rationale**: FR-009 explicitly requires "no new propagation rules" and this function's value is now `kneeRPS` in *both* modes (D1) — since the knee is unchanged by mode, there is nothing mode-dependent to add. Downstream starvation (US3 Acceptance Scenario 1) needs zero changes: it falls out entirely from `computeHostMetrics` now returning a correctly-collapsed `forwardedRPS`, which flows through the existing, untouched `edgeOutputRPS` mechanism to every outbound edge and downstream node. Thematically this is also the more honest model: real congestion collapse/receive livelock happens precisely *because* a system keeps accepting work past the point a well-behaved backpressure mechanism would have refused it — a queue that perfectly throttles to the host's declared cap is exhibiting *clamp*-like graceful degradation, not collapse.

**Known limitation, documented rather than special-cased**: because a queue's desired outflow toward a single saturating host is capped at `kneeRPS` regardless of mode, a host fed *exclusively* by one queue can never itself receive more than `kneeRPS` through that edge — it will sit exactly at the knee (`decay(1) = 1`, identical to clamp) and never visibly collapse through that edge alone. Collapse manifests once a host's *total* incoming (from a second/direct edge, another queue, or multiple inbound edges) exceeds its knee. US3's acceptance scenario ("queue backlog growth rate rises as B collapses") is real and demonstrable, but requires a topology where the collapsing host has more than one path pushing it past its knee — the quickstart's US3 walkthrough uses such a topology (a direct edge plus a queue into the same host) rather than a single-queue-only chain. This is called out here explicitly per FR-009/the spec's Assumptions ("curve family is an engine decision") rather than solved with new cross-window state (e.g., feeding a queue's accept-capacity from the host's previous-window goodput), which would itself be a new propagation mechanism and was rejected as unnecessary complexity for a P2 scenario.

**Alternatives considered**: Feeding `hostAcceptCapacityRPS` from the collapsing host's previous-window `forwardedRPS` (a one-window-lag estimate, following the same "carry state across windows" idiom `queueBacklogGB`/`replicaRuntimeByNode` already use) — rejected: introduces new per-node cross-window engine state and a feedback lag purely to strengthen one P2 acceptance nuance, directly against FR-009's "no new propagation rules" and adding real complexity (new `FlowPropagationInput`/`Output` field, new `simulation.ts` state) for a demo-only benefit already achievable with a two-path topology.

## D5 — `collapsed` status: a new, higher-priority status derived from goodput ratio

**Decision**: `HostNodeMetrics['status']` gains `'collapsed'`. `deriveStatus` checks it **first**, before the existing `overloaded`/`saturated`/`healthy` ladder: when `overloadBehavior === 'collapse'`, `incomingRPS > kneeRPS` (past the knee), and `forwardedRPS < kneeRPS × HOST_COLLAPSE_STATUS_RATIO` (new internal tunable, **0.5** — goodput has fallen below half of peak), status is `'collapsed'`. Otherwise status falls through to the existing ladder unchanged (so a collapse-mode host just past the knee, still near-peak goodput, reads `overloaded` exactly as clamp would, until it degrades further).

**Rationale**: FR-007 requires a distinct status "when a collapse-mode host operates past the knee with materially degraded goodput (threshold internal)" — 0.5 is a defensible, internally-documented "materially degraded" bar with headroom under SC-001's "<20% of peak by 3×" bound (at 3× offered load, goodput is already at ~11% of peak, deep into `collapsed` territory, not hovering at the boundary). Checking collapse first is necessary because past the knee, `rho` (unclamped) is already `> 1` in every case that matters, which would otherwise always report `overloaded` first and make `collapsed` unreachable.

**Alternatives considered**: Threshold expressed as an overload-ratio cutoff (e.g. "collapsed once `x > 2`") instead of a goodput ratio — rejected: a goodput-ratio threshold is what's actually observable/meaningful to a user ("goodput has halved"), and stays correct even if `κ` is retuned later, whereas an `x`-based cutoff would need to move in lockstep with `κ`.

## D6 — Inspector visibility and default value

**Decision**: The new `overloadBehavior` chip control renders in `hostConfigFields.tsx`'s `HostConfigFields`, in the branch already shared by both config modes (after `ManualComputeFields`/`CalculatedComputeFields`, alongside `AutoscalingFields`) — `client_pool` and `external_api` return early before that point today, so FR-006 ("no control for those profiles") holds with no extra conditional. Mode-switch (`handleModeChange` in the same file) carries `overloadBehavior` over unchanged, same as it already does for `minReplicas`/`maxReplicas`/`bootDelayMs`/watermarks. `Inspector.tsx`'s `defaultSimForChoice` sets `overloadBehavior: 'collapse'` for newly-assigned compute profiles (FR-005); `initialDiagram.ts`'s starter hosts get `overloadBehavior: 'collapse'` too (they're code-authored fresh content, not an imported legacy diagram). Import (`exportDiagram.ts`'s `plainNodeSim`) fills in `LEGACY_OVERLOAD_BEHAVIOR_FOR_IMPORT = 'clamp'` (new `config.ts` constant) whenever the field is absent from old JSON — mirroring the exact `LEGACY_BOOT_DELAY_MS_FOR_IMPORT`/watermark pattern already established by 013.

**Rationale**: Matches the established "new parameter, closed-set" UI/import pattern exactly (013 D5/D6), no new UI architecture needed.

## D7 — Formula descriptor: only shown when `overloadBehavior === 'collapse'`

**Decision**: A new `buildHostCollapseDescriptor` in `formulaCatalog.ts`, appended to a host's `formulaDescriptors` array in `flowPropagation.ts` only when `sim.overloadBehavior === 'collapse'` (clamp-mode hosts keep exactly their current descriptor set — SC-003 regression safety extends to the formula panel, not just the numeric metrics). `isBinding: true` once the host is past its knee (`incomingRPS > kneeRPS`), matching the existing `isBinding` convention used by `buildHostShedDescriptor`/`buildHostSaturationDescriptor`.

**Rationale**: US4/FR-011 says the collapse formula should appear "when a collapse-mode host is selected" — gating by mode (not by status) means the formula is visible with its live inputs even below the knee (useful for understanding the curve before it's triggered), consistent with how other descriptors already render regardless of whether they're currently binding.

## D9 — Elastic scaling groups don't use the retrograde curve; overloaded replicas are evicted instead (post-implementation refinement)

**Decision**: After D1–D8 shipped, product feedback identified that applying the smooth per-replica retrograde curve uniformly across an *elastic* scaling group (`minReplicas !== maxReplicas`, feature 013) would implicitly require modeling a single degraded replica gracefully recovering in place — complexity this engine deliberately doesn't take on. Instead, for elastic hosts only:
- **While replicas are alive**, `collapse` behaves exactly like `clamp` (plateau at `effectiveReplicas × kneeRPS`, no retrograde decay) — `computeHostMetrics`'s new `isElasticGroup` flag gates the curve selection in `computeManualMetrics`/`computeCalculatedMetrics`.
- **Overloaded replicas crash and are evicted** instead: `autoscaler.ts#evictCollapsedReplicas` computes `survivors = floor(effectiveReplicas / perReplicaSaturation)` whenever `perReplicaSaturation > 1`, evicting `max(1, effectiveReplicas − survivors)` replicas — immediately, with no cooldown/sustain gate (a crash is a reactive failure, not a throttled policy decision) — and is allowed to drive `nominalCount` below `minReplicas`, all the way to 0.
- **A host with 0 currently-serving replicas is reported as fully dead**: `computeHostMetrics` short-circuits to `forwardedRPS = 0`, `shedRPS = incomingRPS` (100%), `status = 'collapsed'`, and a finite ceiling latency (`hockeyStickLatencyMs` at `HOST_RHO_CLAMP`) — it neither forwards nor meaningfully accepts traffic, matching the product requirement that a collapsed host be "virtually dead."
- **Recovery is the scaler's job, not this feature's**: `autoscaler.ts#restoreMinReplicaFloor` runs once per window, alongside `drainBootQueue` (i.e. at the START of the window AFTER an eviction, not folded into the same `evaluateScaling` call the eviction happened in — see that function's doc for why the one-window offset matters: it's what lets a fully-crashed window's telemetry genuinely read `nominalCount = 0` for at least one window, per the product's "a scaling group with 0 nodes for some momentos" framing, before the floor restore queues fresh booting replicas the next window). The existing high-watermark scale-up path (unchanged) can also push the group past `minReplicas` up toward `maxReplicas` if load is still high once replicas come back.
- **Non-elastic hosts** (`minReplicas === maxReplicas`, whether a true single instance or a fixed multi-replica group with no scaler) are completely unaffected — they keep D1–D8's original smooth retrograde curve and `collapsed`-by-goodput-ratio status exactly as shipped, since there's no scaler to evict into or recover from.
- The formula panel (US4) shows a new `host.replica-eviction` descriptor (same citations: Mogul & Ramakrishnan, Gunther's USL) for elastic collapse hosts, in place of `host.overload-collapse`, which remains exclusive to non-elastic hosts.

**Rationale**: This is a strictly smaller state machine than "retrograde-decay a whole group in place": individual replica lifecycle (die → evicted → scaler notices deficit → boots a replacement) reuses 013's existing boot-delay/watermark machinery entirely — no new replica lifecycle states, no per-replica recovery curve. It also produces a more honest teaching moment for an audience already looking at autoscaling groups: a real orchestrator doesn't gracefully throttle a single failing pod's throughput, it kills and replaces it, and a fleet can legitimately serve at 0 capacity for a stretch under a fast-enough failure cascade.

**Alternatives considered**: Applying D1–D8's curve to the whole group's aggregate capacity (the original shipped behavior) — rejected per the above; folding the floor-restore into the same `evaluateScaling` call as the eviction (tried first) — rejected because it made `nominalCount` bounce back to `minReplicas` in the same window as the crash, so telemetry never actually showed 0 nodes, undermining the whole point of the refinement.

## Branch topology note (why `dev` was merged first)

`012-overload-collapse` was cut from the `011-host-queue-model` merge commit (`7b08d13`), *before* `013-host-autoscaling` was built and merged into `dev` (constitution 3.0.0 → 3.3.0, `HostNodeSim`'s saturating variants gaining `minReplicas`/`maxReplicas`/`bootDelayMs`/`highWatermark`/`lowWatermark`, `hostModel.ts`'s per-replica division). Per the standing lesson from feature 010 (always check `git branch -a`/`git log` for a dependency feature's branch before planning against an assumed contract), `dev` was merged into `012-overload-collapse` before this research began, so this plan is written against the *current*, post-013 shape of `HostNodeSim`/`hostModel.ts`/`flowPropagation.ts` — not the pre-013 011 baseline the spec was originally drafted against. The only merge conflict was `.specify/feature.json`'s `feature_directory` pointer, resolved to `specs/012-overload-collapse`.
